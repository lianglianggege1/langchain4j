GOAP 运行模式：用 writer 实例拆解规划、搜索与运行时

目标导向行为规划（Goal-Oriented Action Planning）——只声明「动作」的前置条件与效果，让规划器自己搜索出通往目标的路径。

本课的收获（一个可验证的小胜利）：读完这一课，你应该能不看资料，独立画出 writer 实例的依赖图，并说出从 writer.write(...) 到返回故事的运行时每一步。所有结论都取自本地仓库源码，每处关键论断都附文件定位，你可以随时跳过去验证。

1. 从「编排」到「规划」

传统 workflow（如 SequentialPlanner、LoopPlanner）要求你事先指定执行顺序：先 A 后 B 再 C。而 GOAP 反其道而行之——你只声明每个 agent「需要什么、产出什么」，再给定一个目标，规划器在运行时搜索出一条从当前状态到目标的最短动作序列。

一个类比：传统 workflow 是你手写导航路线；GOAP 是你只报目的地，导航自己算路。状态是「你现在的位置」，agent 是「道路」，目标是你设定的 outputKey。

GOAP 三要素（对应本模块的实现） 前置条件（preconditions）：agent 的输入参数对应的 state key，即 @V("...") 标注的名字； 效果（effects）：agent 执行后写入 scope 的 outputKey； 目标（goal）：规划根代理（writer）的 outputKey。

GOAP 思想起源于游戏 AI——Jeff Orkin 在 GDC 2006 上讲述 F.E.A.R. 的机器人 AI 时提出：把行为建模为「前置条件 + 效果」的动作，运行时用搜索代替手工状态机。这个思想被原样搬进了 langchain4j 的 GoalOrientedPlanner。读完本课后，推荐精读这篇原始论文（本课首选延伸阅读）。

第一层（GoalOrientedSearchGraph.search）做翻译：把 scope 中已有的 key（作为前置条件）和 goal 节点交给底层搜索器。注意一个过滤动作：scope 里存在但图中没有的 key（比如测试监听器故意写入的 additionalKey）会经 nodes::get + filter(nonNull) 被直接丢弃——这正是 GoapWriterIT 里 GoapListener 想验证的容错点。

第二层（DependencyGraphSearch.search）是改造版 A*：

A* 概念本实现
状态 g(n)SearchState = 已激活节点集合 + 当前节点 + 深度
邻居扩展findActivatableNodes：已激活节点的输出中，所有输入依赖都已满足的节点
启发函数 h(n)从目标向下收集「尚未激活」的节点个数（可采纳：不会高估）
每步代价固定 1.0（激活一个节点）
路径重构reconstructPath：沿 cameFrom 回溯，提取每一步「新激活」的节点

writer 实例的搜索轨迹：初始激活集 {topic, style, audience} → 要激活 finalStory 缺 styledStory → 要激活 styledStory 缺 story → 要激活 story 缺 topic（已有）。于是节点路径为：

{topic, style, audience} → story → styledStory → finalStory

search() 的后半段把节点路径翻译回 agent 路径：跳过本来就是前置条件的节点，对其余每个输出节点沿边回查「哪个 agent 能产出它」。最终得到（并打出一行 LOG.info）：

Agents path sequence: [storyGenerator, styleReviewLoop, audienceEditor]

4. Runtime：谁在驱动这一切

规划器只是「决策者」，真正跑循环的是 PlannerBasedInvocationHandler 内部的 PlannerLoop（langchain4j-agentic/src/main/java/dev/langchain4j/agentic/internal/PlannerBasedInvocationHandler.java:418）。两者的分工是：运行时持有并传递 AgenticScope（全局黑板），反复问规划器「下一步干嘛」；规划器返回 Action，运行时负责执行。

逐行对应

// PlannerBasedInvocationHandler.executeAgentMethod(...)
DefaultAgenticScope currentScope = currentAgenticScope(registry, method, args);
writeAgenticScope(currentScope, method, args);          // topic/style/audience 写入黑板

Planner planner = plannerSupplier.get();
planner.init(new InitPlanningContext(currentScope, this, subagents));

result = new PlannerLoop(planner, currentScope, registry).loop();   // 核心

Object output = outputKey != null ? currentScope.readState(outputKey) : result;

PlannerLoop.loop()（同文件 437-478 行）就是图 2 中的循环体：先尝试恢复执行状态，然后 firstAction() 进入 while (!isDone())；每个 agent 执行完毕回调 onSubagentInvoked()（568-581 行），在其中调用 planner.nextAction(...) 取下一个 Action，同时 saveExecutionState() + agenticScope.checkpoint() 落检查点。GOAP 的 executionState() 永远返回空 Map——它天生无状态。

崩溃恢复：无状态即自愈 GoalOrientedPlanner.restoreExecutionState() 是故意的空实现（GoalOrientedPlanner.java:42-58 注释）。恢复执行时，firstAction() 会拿当前 scope 重新搜索：已执行完的 agent 输出已在黑板上，重算出的路径天然只含「剩下的」agent，游标从 0 重新开始。持久化游标反而有害——失效游标可能越界。

内层循环的运行时

当运行时执行到 styleReviewLoop 这个 Action 时，它其实执行的是又一个 PlannerBasedInvocationHandler——里面对应的规划器是 LoopPlanner（workflow/impl/LoopPlanner.java:56-69）：光标在 subAgents 上环形推进（(cursor+1) % agents.size()），每跑完一整圈检查一次退出条件——iterationsCounter >= maxIterations(5) 或 exitCondition(scope) == score ≥ 0.8。所以 writer 实例的完整执行序列是：

storyGenerator          → story    = "很久很久以前，龙与巫师…"
styleReviewLoop 第1圈    → styledStory = 文风改写版（story + style）
              styleScorer → score    = 0.6  < 0.8 → 继续循环
styleReviewLoop 第2圈    → styledStory = 再次改写
              styleScorer → score    = 0.85 ≥ 0.8 → 退出循环
audienceEditor           → finalStory = 面向 young adults 的最终版

测试最后的断言 readState("score") ≥ 0.8 和「styleEditor 必须先于 audienceEditor 执行」的监听器校验，都是对上述序列的行为验证。

6. 检索练习

先在脑中作答，再点开核对。回忆比重看一遍有效得多。

Q1. GOAP 的「目标」（goal）从哪里来？

规划根代理（Writer）的 outputKey。在 init() 里取 initPlanningContext.plannerAgent().outputKey()，本例即 "finalStory"。

Q2. 依赖图中的「节点」和「边」分别由什么构成？

节点 = AgenticScope 中的 state key；边 = 一个 subAgent，连接它的每个输入 key 节点到它的输出 key 节点（GoalOrientedSearchGraph.init）。

Q3. 监听器往 scope 里塞了一个图中不存在的 additionalKey，搜索会发生什么？

什么都不会发生。preconditions 先经 nodes::get 再 filter(Objects::nonNull)，图中无对应节点的 key 被静默丢弃——这正是 GoapWriterIT 的 GoapListener 想验证的容错行为。

Q4. 进程崩溃后恢复执行，GoalOrientedPlanner 如何「续上」？

它不保存任何状态（executionState() 返回空 Map，restoreExecutionState() 为 no-op）。恢复时 firstAction() 拿当前 scope 重新搜索：已完成 agent 的输出已在黑板上，重算路径只含剩余 agent，游标自然从 0 开始。

Q5. 为什么 styleScorer 不出现在顶层依赖图里？

GOAP 图只由 planner 直接注册的 subAgents（storyGenerator、styleReviewLoop、audienceEditor）构建。styleScorer 是循环的内部子代理，循环对外只是一个「story + style → styledStory」的单个动作，内部由 LoopPlanner 驱动。

Q6. 如果一个 Action 里带多个 agent，运行时怎么执行？GOAP 场景下会出现吗？

PlannerLoop 用 CompletableFuture 并行执行全部 agent。GOAP 的 A* 产出的是线性激活序列，每次只 call() 一个 agent，所以 writer 实例里不会出现并行分支；并行是给其他规划器（如 ParallelPlanner）准备的通道。

  • 速查手册：本课配套的 GOAP 运行时速查表，浓缩了接口、图规则与时序，适合打印贴在手边。
  • 同门对照：blackboard 模式（你已学过它的 HITL）是「无规划、各方自由写黑板」；GOAP 是「先搜出计划再按序执行」——同一块黑板，两种调度哲学。
