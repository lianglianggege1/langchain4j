Voting 模式：并行投票与共识聚合

VotingPlanner + VotingStrategy —— 不决定「先做谁」，而是让所有投票者同时上钟，最后把一堆答案聚合成一个。

本课的收获：读完这一课，你应该能脱稿画出 classifier 实例的 fan-out/fan-in 图，说清「一票从产生到被计入」的完整运行时路径，并且能独立推演出 VotingPlanner 的一个隐藏坑（崩溃恢复）。前提是你已学过 第 1 课（GOAP 与 PlannerLoop 运行时）——本课全程复用那里的运行时知识。

1. 一句话定位：GOAP 的镜像

用你熟悉的算法语言说：GOAP 是在依赖图上搜一条最短路（决策「顺序」），Voting 是一次扇出-汇聚（求「共识」）。它就是集成学习（ensemble learning）在智能体框架里的直系亲戚——随机森林对多棵树做多数表决，这里对多个 LLM 投票者做聚合。LLM 侧的理论根基是 Self-Consistency：对同一问题采样多条推理路径再表决，准确率显著高于单路推理（本课首选延伸阅读，文末有链接）。

2. VotingPlanner：全文 57 行走读

整个规划器只有四个状态字段和一个决策循环，比 GOAP 简单一个数量级：

public class VotingPlanner implements Planner {
    private final VotingStrategy strategy;   // 聚合规则（注入）
    private List<AgentInstance> subagents;  // 投票者名单（init 时拿到）
    private int completedCount;               // 已收回的票数
    private final List<Object> votes = new ArrayList<>(); // 票箱（内存）

    public Action firstAction(PlanningContext ctx) {
        if (subagents.isEmpty()) return done();
        return call(subagents);              // ★ 一口气 call 全部 → 运行时并行派发
    }

    public Action nextAction(PlanningContext ctx) {
        votes.add(ctx.previousAgentInvocation().output());  // ★ 票 = agent 的返回值
        completedCount++;
        if (completedCount < subagents.size())
            return noOp();                    // 票没收齐：空转等待
        return done(strategy.aggregate(votes)); // 票齐：聚合出最终结果
    }
}

voting/VotingPlanner.java:13-57

四个关键观察：

  • 并行从哪来：call(subagents) 把所有投票者塞进一个 Action——第 1 课讲过，PlannerLoop 对多 agent 的 Action 用 CompletableFuture.allOf 并行执行。VotingPlanner 自己一行并发代码都没写。
  • 票是什么：previousAgentInvocation().output() 是 agent 的返回值（如 "POSITIVE"、CritiqueResult record），不是从黑板 state 读的——所以三个投票者即使 outputKey 撞车，票也不会丢；但实例里仍给每人独立 outputKey（vote1/2/3），是为了黑板上留痕可审计。
  • 收票是线程安全的：三个并行 agent 各自完成时都会回调 onSubagentInvoked()（第 1 课时序图第 5 步），内部用 ReentrantLock 串行化地调 nextAction()——votes.add 全程持锁，票箱不会脏。
  • noOp 的用途：前 N−1 张票到达时无事可做，返回 NoOpAction（空 agent 列表的 AgentCallAction）占位；最后一张票到达时返回 done(aggregate)。PlannerLoop 的 composeActions 会把中间的 noOp 吞掉、让 done 生效。

3. VotingStrategy：聚合规则即扩展点

@FunctionalInterface
public interface VotingStrategy {
    Object aggregate(Collection<Object> votes);

    static VotingStrategy majority() { ... } // 分组计数，取出现最多的值
    static VotingStrategy average()  { ... } // 数值票求均值
    static VotingStrategy highest()  { ... } // Comparable 票取最大
}

voting/VotingStrategy.java:9-37

三个内置策略各对应一种集成学习惯例：majority = 随机森林式表决，average = 回归集成取均值，highest = 「乐观边界」。而它是个 @FunctionalInterface——意味着聚合逻辑可以是任意函数，critic 实例正是靠自定义聚合器把「投票」变成了「评审团合议」（见第 5 节）。

内置 majority 的两个坑 ① 平票无仲裁：三个投票者若给出三个互不相同的答案，计数全是 1，max 只取 HashMap 遍历中碰到的第一个——结果不确定。要确定性平票裁决，得自己写策略（比如加权重）。② 等值靠 equals：LLM 返回 "POSITIVE"、"Positive."、" positive" 会被当成三张不同的票——所以 classifier 的 prompt 里才反复强调 Reply with exactly one word，这是用提示词工程在给 majority() 的语义兜底。

5. 实例二：critic（Voting 的完全体）

critic 实例把 Voting 嵌进了一个更大的复合系统，一次展示三个新能力：自定义聚合器、按状态动态选模型、投票 × 循环 × 顺序的嵌套。

三个新能力逐一点名：

① 自定义聚合器 = 投票变合议。critic 的票不再是字符串而是 CritiqueResult(score, suggestions) record，聚合函数自己写：分数取均值、建议拼接。此时「Voting」的本质显露无遗——它只是「并行扇出 + 任意收敛函数」，majority 只是个特例：

static VotingStrategy critiquesAggregator() {
    return votes -> {
        var critiques = votes.stream().map(v -> (CritiqueResult) v).toList();
        double averageScore = critiques.stream().mapToDouble(CritiqueResult::score).average().orElse(0.0);
        String allSuggestions = critiques.stream().map(CritiqueResult::suggestions)
                .collect(Collectors.joining("; "));
        return new CritiqueResult(averageScore, allSuggestions);
    };
}

7. 检索练习

Q1. VotingPlanner 的「票」从哪里来？为什么不从黑板读？

来自 planningContext.previousAgentInvocation().output()，即每个 agent 的方法返回值。从黑板读会有覆盖问题（三个投票者写同一个 key 只剩最后一份），而返回值在每次调用回调时独立送达——票天然不会互相冲掉。

Q2. VotingPlanner 自己没写任何并发代码，并行是谁做的？

PlannerLoop 运行时：Action 里带多个 agent 时走 parallelExecution()（CompletableFuture.allOf）。规划器只负责「一个 Action 塞 N 个 agent」这个声明，执行机制是运行时的通用能力——GOAP 是同一机制下「每 Action 只 1 个」的退化用法。

Q3. classifier 的三个 prompt 人设为什么故意不同？

投票的价值来自错误不相关（集成学习原理）：三个不同视角各自犯错的位置不同，多数表决才能纠错。若三份 prompt 完全相同，就是三倍成本买一份答案。Self-Consistency 论文用温度采样制造多样性，这里用 prompt 人设制造——同一原理的两种实现。

Q4. done(strategy.aggregate(votes)) 的聚合结果是怎么到达调用方的？

PlannerLoop.result() 拿到 DoneWithResultAction.result()（聚合值），若规划根有 outputKey 则 writeState(outputKey, 聚合值)（classifier 的 "classification"、critic 的 "critique" 都是这么写进黑板的）再返回；方法返回值即聚合结果。

Q5.（推演题，第 1 课知识的迁移）假设三个投票者已并行完成 2 个时进程崩溃，恢复执行会发生什么？

会出问题：votes 和 completedCount 只在规划器实例内存里（executionState() 未持久化，恢复后清零）；而 PlannerLoop 的 filterCompletedAgents 会把已完成的 2 个 agent 从重发的 call() 里剔除，只重跑剩下的 1 个——completedCount 最多到 1，永远凑不齐 subagents.size()=3，nextAction 持续返回 noOp，主循环空转（活锁）。根因：GOAP 的自愈靠「黑板状态可重搜」，而投票的票源是「调用返回值」这种易失事件，黑板里救不回来。结论：Voting 适合短平快的并行任务，别指望它挂起续跑。

Q6. critic 实例里 majority 一张票都没用上，那 VotingPlanner 在其中的作用还剩什么？

剩下的是模式骨架：并行扇出（3 个评审同时跑）+ 票齐才收敛 + 聚合函数决定收敛结果。VotingStrategy 是可替换的收敛函数——critiquesAggregator 把「表决」换成「合议」（均值分 + 拼接建议）。换句话说 VotingPlanner ≈ 并行 fan-out/fan-in 的骨架，majority 只是默认收敛函数。
