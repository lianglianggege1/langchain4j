P2P 模式：数据驱动的对等协作

没有指挥官，只有一块共享黑板（AgenticScope）——谁的输入齐了谁上，谁依赖的数据变了谁重跑。

本课的收获（一个可验证的小胜利）：读完这一课，你应该能不看资料，对着 P2PResearcherUntyped 说出从 invoke("produce a research about black holes") 到返回 hypothesis 的每一轮激活序列，并解释为什么 P2PPlannerTest 里那对 ping-pong agent 恰好执行 max 次。所有结论取自本地源码，关键论断附文件行号，可随时跳转验证。

1. P2P 是什么：从「谁决定下一步」说起

把本仓库学过的编排模式放到同一把尺子下——「下一步执行谁」由谁决定——差异立刻显现：

模式谁决定下一步决定依据拓扑
Sequence / Loop写代码的人事先写死的顺序SEQUENCE / LOOP
SupervisorLLM（每次现问）对话上下文 + 子 agent 描述AI_AGENT
GOAP（第 1 课）搜索算法前置条件/效果 + 目标，一次规划出整条路径图搜索
P2P（本课）数据本身「我的输入都齐了吗」+「我依赖的数据变了吗」STAR（scope 为中心）

P2P（peer-to-peer，对等网络）模式里，P2PPlanner 不做任何"聪明"的决策——它是一个机械的激活引擎：扫描所有子 agent，谁的输入参数在共享状态里全部就绪，就调度谁；某个 agent 写出的结果恰好是别人的输入，别人就被自动激活；如果某 agent 依赖的数据被更新了，它还会被标记为"变脏"而重新执行。agent 彼此之间从不直接调用，一切通信都经由中心的 AgenticScope——这正是 topology() 返回 AgenticSystemTopology.STAR 的含义P2PPlanner.java:199-201。

与 blackboard 模式对照（你已学过） blackboard 里知识源（KS）由仲裁器挑选下一个触发；P2P 把这套逻辑简化到了极致：输入齐全即触发（无需仲裁优先级），输入变更即重跑（响应式语义）。可以把它理解为"黑板 + 数据流激活"的合体，非常适合流水线式多 agent 协作，但环依赖会振荡（第 8 节）。

6. 内部逻辑深潜：AgentActivator 状态机

P2P 的全部"智能"浓缩在 P2PPlanner 的私有内部类 AgentActivator 里P2PPlanner.java:128-173。每个子 agent 对应一个 activator，持有两个 volatile 布尔位——一个是「锁」，一个是「脏位」：

  • executing（锁位）：这个 agent 当前是否在执行。用于并行场景下防止重复调度、防止误判稳定态。
  • shouldExecute（脏位，初始 true）：数据是否要求我（重新）执行。激活即消费掉脏位，输入被改又置回。

围绕这组标志位，三个决策方法各司其职：

nextCallAction —— 扫描与收集P2PPlanner.java:106-122

AgentInstance[] agentsToCall = agentActivators.values().stream()
        .filter(a -> a.canActivate(agenticScope))   // 锁未占 ∧ 脏 ∧ 输入齐
        .peek(AgentActivator::startExecution)       // 立刻上锁、清脏位
        .map(AgentActivator::agent)
        .toArray(AgentInstance[]::new);

if (agentsToCall.length == 0 && agentActivators.values().stream().noneMatch(AgentActivator::isExecuting)) {
    return done();   // 没人能跑，也没人在跑 → 稳定态
}
invocationCounter += agentsToCall.length;
return call(agentsToCall);   // 可能是空数组 → "暂不决策"

注意两个易错点：（a）收集与上锁在同一个流里原子完成，扫描到的 agent 立刻 startExecution，不会在下一次扫描中重复出现；（b）「没人能跑」不等于「结束了」——必须同时没人正在跑才算稳定态，否则返回空 call()，让主循环 Thread.yield() 干等下一个完成回调（图 2 右上的琥珀分支）。

nextAction —— 终止判断 + 变脏广播P2PPlanner.java:91-104

if (terminated(agenticScope)) return done();          // 先查闸门

AgentActivator lastExecutedAgent = agentActivators.get(planningContext.previousAgentInvocation().agentId());
if (lastExecutedAgent != null) {
    lastExecutedAgent.finishExecution();              // 解锁
    agentActivators.values()                          // 变脏广播：
        .forEach(a -> a.onStateChanged(lastExecutedAgent.agent.outputKey()));
}                                                     // 输入含此 key 的 activator 全部置脏
return nextCallAction(agenticScope);

变脏广播是 P2P 响应式语义的核心：刚完成的 agent 把自己的 outputKey 吆喝给所有 activator，谁的输入名单里含这个 key，谁的脏位就被置回——哪怕它刚跑完，哪怕它正在跑。这就是图 1 里红回边「写回 hypothesis」能驱动 Critic/Validation/Scorer 无限循环的机制根源。

firstAction —— 冷启动P2PPlanner.java:73-88

只在 scope 含 p2pRequest 时做一次 LLM 变量提取（第 2 节第三步），然后直接进入 nextCallAction。typed 入口（如 ResearchAgent.research(@V("topic"))）没有 p2pRequest，这一步整体跳过——同一个 P2PPlanner，两种引导方式。

执行侧：PlannerLoop 主循环PlannerBasedInvocationHandler.java:437-478

nextAction = planner.firstAction(new PlanningContext(agenticScope, null));
while (nextAction == null || !nextAction.isDone()) {
    if (nextAction == null) { Thread.yield(); continue; }
    List<AgentExecutor> agents = ((Action.AgentCallAction) nextAction).agentsToCall();
    nextAction = null;
    switch (agents.size()) {
        case 0  -> Thread.yield();            // 空动作：等待下一个完成回调
        case 1  -> agents.get(0).execute(agenticScope, this);
        default -> parallelExecution(agents);  // CompletableFuture.allOf 并行
    }
}

agent 执行完毕后，AgentExecutor.completeAgentInvocation 依次做三件事：把返回值 writeState(outputKey, response) 写进 scope、登记 AgentInvocation（供审计与恢复）、回调 planner.onSubagentInvoked(...)AgentExecutor.java:97-122。回调在 ReentrantLock 内执行 composeActions(当前动作, planner.nextAction(...))PlannerBasedInvocationHandler.java:568-581——并行批里两个 agent 一先一后完成时，两次决策的动作会被合并成一个大 call，而不是后者覆盖前者:588-600。另外每次回调都会把 invocationCounter 等执行态存进 scope（executionState()），崩溃后可恢复P2PPlanner.java:185-196。

7. 终止的三重保险：用单测逐个验证

P2P 没有天然的"结束"——数据流可能永远流下去。运行时的出口有三个，P2PPlannerTest 用纯 Java agent（无 LLM）把它们逐一钉死：

保险判定处验证测试
① 稳定态（quiescence）nextCallAction：无人可激活 ∧ 无人执行should_terminate_when_no_agent_can_be_activated_anymore
② 硬闸：次数上限terminated()：counter ≥ maxshouldNotInvokeMoreAgentsThanMaxAgentsInvocations
③ 软闸：exit 条件terminated()：exitCondition(scope, counter)shouldStopBeforeMaxAgentsInvocationsWhenExitConditionIsMet

保险 ②：ping-pong 精确执行 max 次P2PPlannerTest.java:30-57

pingAgent:  @Agent(outputKey="ping")  ping(@V("pong"))  → "ping-" + pong
pongAgent:  @Agent(outputKey="pong")  pong(@V("ping"))  → "pong-" + ping
// 种子：invokeWithAgenticScope(Map.of("pong", "seed"))

这两个 agent 互为输入输出，永远有活干——稳定态永远达不到，唯一出口是硬闸。手推 max=3 的轨迹：

轮次决策执行counterscope 新变化
1ping canActivate（pong 已种子化）ping → ping-seed1ping 写入 → pong 置脏
2pong canActivatepong → pong-ping-seed2pong 被改 → ping 置脏
3ping canActivate（脏位回来了）ping → ping-pong-ping-seed3—
—nextAction：3 ≥ 3 → terminated——done()，断言 invocations == 3 ✓

参数化跑 max = 1/3/6/10，断言全部精确命中——因为 terminated() 在每次完成回调的开头就检查，一个不多、一个不少P2PPlannerTest.java:46-57。把 max 换成 exit 条件 invocationCounter >= 2，同样精确停在 2 次P2PPlannerTest.java:59-69。

保险 ①：无环 DAG 自然沉降P2PPlannerTest.java:93-117

producer（零输入）写 key1，consumer 读 key1 写 result2，没有 exit 条件、上限放宽到 15。轨迹：producer 先跑（零输入 agent 天然可激活）→ key1 出现 → consumer 激活 → result2 出现但没有任何 agent 的输入名单里有 result2，无人在跑、无人变脏 → done()。DAG 一定会沉降到稳定态，这是无环依赖的数学保证。

防"假稳定"：还有人干着活呢P2PPlannerTest.java:119-160

最精妙的一个测试。slowConsumer 和 fastConsumer 并行（都被 key1 激活），fastConsumer 先完成时，用 CountDownLatch 强制 slowConsumer 还挂在半路。此刻 nextCallAction 的扫描结果：无人可激活（slowConsumer 锁位占着）——如果只看这一半条件就会误判稳定态、提前 done()，slowConsumer 的 result2 就永远丢了。正是 noneMatch(AgentActivator::isExecuting) 这半个条件救了场：返回空动作 → 主循环 yield → slowConsumer 完成后再决策 → 正确沉降。

防"冻结"：composeActions 回归P2PPlannerComposeActionsIT.java:55-108

同样的 producer + 双 consumer 结构（随机 sleep 制造完成顺序的不确定性），exit 条件是 result2 和 result3 都在。测试的失败信息直言病灶："composeActions likely dropped a done() action in favor of an empty call()"。设想并行批里 A 先完成且触发了 done()，而 B 随后完成时又产生一个空 call()——如果合成逻辑拿空动作覆盖了 done，主循环就永远 yield() 下去：没人会再完成，没人会再决策。现在的 composeActions 明确把空 call 当作「可丢弃」的一方，done 优先PlannerBasedInvocationHandler.java:588-600。

记忆口诀 空动作 = "我暂时不决策"，done = "我永远不决策"。合成时后者赢；扫描时"无人可激活"必须叠加"无人执行中"才能升级成 done。

8. 被禁用的 IT：P2P 的两个坑

P2PResearcherIT.p2p_tests() 至今挂着 @Disabled("TODO: fix. It enters an infinite loop")P2PResearcherIT.java:15-17。它是全模块唯一的"真实 LLM"P2P 集成测试，恰好也是两大风险的临床标本：

坑一：环依赖 → 结构性振荡。回看图 1：Validation 写 hypothesis，而 hypothesis 是 Critic、Validation（自己！）、Scorer 三者的输入。每一轮 Validation 的修订都会把这三家全部置脏，新一轮并行批又会写出新的 critique / hypothesis / score……如果 LLM 打分始终到不了 0.85，理论上只有硬闸（本例 max=10）能拦住。真实 LLM 的输出不确定性 + 环依赖，就是无限循环的温床。设计 P2P 系统时，先画出依赖图——凡是有回边的，必须同时配备硬闸（maxAgentsInvocations）与可收敛的软闸（exitCondition），缺一不可。

坑二：空动作自旋 → 运行时冻结。即使没有环，历史版本也曾因 composeActions 的合成缺陷而"冻结"：done 动作被空 call 覆盖后，主循环在 Thread.yield() 上永远空转——没有任何在途 agent 会再来唤醒它。上一节的 ComposeActionsIT 就是针对这个缺陷的回归测试。这两个坑一个在设计层（你的依赖图形状），一个在运行时层（动作合成的正确性），排查 P2P 问题时先问自己：是图有环，还是循环被冻结？

9. 测验：不看源码，凭图推演

Q1 · P2PPlanner 判断一个 agent「此刻可激活」需要同时满足哪三个条件？

① 锁位空闲（executing == false）；② 脏位为真（shouldExecute == true）；③ 它的全部输入名都已在 AgenticScope 中就绪。三者缺一不可，见 canActivate（P2PPlanner.java:145-147）。

Q2 · 扫描时「没有任何 agent 可激活」，planner 一定返回 done() 吗？为什么？

不一定。必须再叠加「也没有任何 agent 正在执行」才判稳定态返回 done()；若还有人执行中，则返回空 call() 让主循环等待——否则会丢掉在途 agent 的产出（假稳定）。

Q3 · ping-pong 测试中 max=3 时，为什么恰好执行 3 次而不是 4 次？

因为 terminated() 在每次完成回调的 nextAction 开头检查：第 3 次执行完 counter==3 已达上限，第 4 次的 call 在生成前就被 done() 拦下，所以精确等于 3。

Q4 · ValidationAgent 的 outputKey 为何会引发振荡？给出修复思路。

它写回的 hypothesis 恰是 Critic、自己和 Scorer 的输入，每轮修订都把三者置脏形成自持回路。修复：让 Validation 写入独立的 key（如 refinedHypothesis）断开回边，或确保 exit 条件必然收敛。
